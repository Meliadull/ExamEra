# ТЕХНИЧЕСКОЕ ЗАДАНИЕ

## на разработку веб-платформы электронного тестирования и анализа знаний учащихся

**Рабочее название проекта:** ExamEra
**Тип системы:** веб-информационная система
**Назначение:** проведение электронного тестирования учащихся, автоматическая проверка результатов, формирование отчётности и аналитики для преподавателей и администрации.

---

# 1. Общие сведения

## 1.1. Наименование системы

Веб-платформа электронного тестирования учащихся **ExamEra**.

Рабочее название может быть изменено на последующих этапах разработки без изменения функциональной концепции системы.

## 1.2. Основание для разработки

Система создаётся с целью перехода от бумажного тестирования учащихся к централизованному электронному формату.

Платформа должна позволять преподавателю:

- создавать или загружать тесты;
- назначать тесты учащимся;
- контролировать сроки прохождения;
- автоматически получать результаты;
- анализировать успеваемость;
- выявлять сложные вопросы и темы;
- формировать отчёты.

Учащиеся должны иметь возможность проходить назначенные им тесты через компьютер, планшет или смартфон.

---

# 2. Цель проекта

Основная цель проекта — разработка единой цифровой системы для автоматизации процессов тестирования, проверки и анализа знаний учащихся.

Система должна заменить значительную часть бумажного тестирования электронным форматом.

Основной бизнес-процесс:

**Преподаватель → создаёт/загружает тест → назначает учащимся → учащиеся проходят тест → система автоматически проверяет ответы → формирует результат → преподаватель получает отчёт и аналитику.**

---

# 3. Основные задачи системы

Система должна обеспечивать:

1. регистрацию и авторизацию пользователей;
2. разграничение прав доступа;
3. управление пользователями;
4. создание учебных групп;
5. создание предметов;
6. создание и загрузку тестов;
7. назначение тестов учащимся;
8. электронное прохождение тестирования;
9. автоматическую проверку ответов;
10. расчёт результатов;
11. хранение истории попыток;
12. анализ результатов тестирования;
13. формирование индивидуальных и групповых отчётов;
14. экспорт результатов;
15. ведение журнала действий пользователей;
16. аудит действий в системе;
17. административное управление платформой.

---

# 4. Типы пользователей системы

В системе предусматриваются четыре основные роли:

### 4.1. Ученик

Ученик является основным участником тестирования.

Ученик должен иметь возможность:

- зарегистрироваться;
- авторизоваться;
- просматривать свой профиль;
- видеть назначенные тесты;
- видеть сроки прохождения тестов;
- начинать тестирование;
- отвечать на вопросы;
- завершать тестирование;
- видеть результат, если преподаватель разрешил его отображение;
- просматривать историю своих тестирований;
- видеть количество набранных баллов;
- видеть процент правильных ответов.

Ученик не должен иметь доступа к правильным ответам до окончания тестирования.

---

## 4.2. Учитель / преподаватель

Преподаватель должен иметь возможность:

- создавать предметы;
- работать с учебными группами;
- добавлять учащихся в группы;
- создавать тесты;
- редактировать собственные тесты;
- копировать тесты;
- архивировать тесты;
- назначать тест учащимся или группам;
- устанавливать время начала и окончания тестирования;
- устанавливать продолжительность тестирования;
- устанавливать количество попыток;
- включать случайное перемешивание вопросов;
- включать случайное перемешивание вариантов ответов;
- просматривать результаты;
- просматривать статистику;
- анализировать результаты учащихся;
- анализировать отдельные вопросы;
- экспортировать результаты.

Преподаватель должен иметь доступ только к тем учащимся, группам и тестам, на которые ему предоставлены соответствующие права.

---

## 4.3. Администратор

Администратор имеет максимальные административные права.

Функции администратора:

- управление пользователями;
- создание пользователей;
- блокировка пользователей;
- восстановление доступа;
- изменение ролей;
- создание преподавателей;
- создание учащихся;
- создание групп;
- управление предметами;
- управление учебными периодами;
- просмотр всех тестов;
- просмотр результатов;
- управление системными настройками;
- управление правами доступа;
- просмотр журнала аудита;
- управление справочниками;
- просмотр общей статистики системы.

Администратор не должен иметь возможности просматривать пароли пользователей в открытом виде.

---

## 4.4. Аудитор

Роль **Аудитор** предназначена для контроля работы системы.

Аудитор получает доступ в режиме **только для чтения**.

Аудитор может:

- просматривать список пользователей;
- просматривать тесты;
- просматривать результаты;
- просматривать статистику;
- просматривать действия преподавателей;
- просматривать административные изменения;
- работать с журналом аудита;
- применять фильтры;
- формировать отчёты;
- экспортировать разрешённую информацию.

Аудитор не может:

- изменять тесты;
- изменять оценки;
- создавать пользователей;
- удалять данные;
- менять роли;
- редактировать результаты тестирования.

---

# 5. Регистрация пользователей

Система должна поддерживать несколько вариантов регистрации.

## 5.1. Регистрация по номеру телефона

Пользователь вводит:

- номер телефона;
- имя;
- фамилию;
- пароль, если используется парольная модель.

На указанный номер отправляется одноразовый код подтверждения OTP.

После успешного подтверждения номера создаётся учётная запись.

Номер телефона должен быть уникальным.

---

## 5.2. Регистрация через Google

Пользователь должен иметь возможность зарегистрироваться и войти с использованием Google Account.

При регистрации система получает разрешённые Google данные, например:

- имя;
- фамилию;
- адрес электронной почты;
- идентификатор аккаунта;
- фотографию профиля, если разрешено.

Email должен использоваться как уникальный идентификатор учётной записи.

---

## 5.3. Вход

На странице входа необходимо предусмотреть:

- вход по номеру телефона;
- вход через Google;
- восстановление доступа;
- функцию «Запомнить меня»;
- выход из аккаунта.

---

# 6. Пользовательский профиль

Профиль пользователя должен содержать:

- фотографию;
- имя;
- фамилию;
- роль;
- номер телефона;
- email;
- учебную группу;
- статус аккаунта;
- дату регистрации.

Пользователь должен иметь возможность изменять разрешённую персональную информацию.

Изменение критически важных данных должно фиксироваться в журнале аудита.

---

# 7. Учебные группы

Система должна поддерживать создание учебных групп.

Пример:

**9-А класс**

или:

**1 курс — группа 101**

Группа содержит:

- название;
- учебный год;
- список учащихся;
- закреплённых преподавателей;
- предметы;
- статус.

Учащийся может быть добавлен в одну или несколько групп в зависимости от организации учебного процесса.

---

# 8. Предметы

В системе должен существовать справочник предметов.

Например:

- Математика;
- Физика;
- Информатика;
- Английский язык;
- История;
- Химия;
- Биология.

Для каждого предмета могут быть определены:

- название;
- описание;
- преподаватели;
- группы;
- тесты;
- тематические разделы.

---

# 9. Создание тестов

Для преподавателя необходимо разработать визуальный **конструктор тестов**.

Карточка теста содержит:

- название;
- предмет;
- тему;
- описание;
- инструкцию;
- количество вопросов;
- максимальный балл;
- продолжительность;
- количество разрешённых попыток;
- дату начала;
- дату окончания;
- статус.

Статусы теста:

- Черновик;
- Опубликован;
- Завершён;
- Архивирован.

---

# 10. Типы тестовых вопросов

Минимальная версия системы должна поддерживать следующие типы.

### Тип 1. Один правильный ответ

Например:

Какой результат выражения 5 × 4?

- 10
- 15
- 20
- 25

Правильный ответ: 20.

---

### Тип 2. Несколько правильных ответов

Пользователь может выбрать несколько вариантов.

Система должна учитывать все правильные ответы согласно установленным правилам оценивания.

---

### Тип 3. Да / Нет

Варианты:

- Да
- Нет.

---

### Тип 4. Верно / Неверно

Подходит для проверки утверждений.

---

### Тип 5. Короткий текстовый ответ

Учащийся вводит ответ вручную.

Для автоматической проверки преподаватель может определить один или несколько допустимых вариантов ответа.

---

# 11. Содержание вопроса

Вопрос должен иметь возможность содержать:

- текст;
- изображение;
- формулу;
- таблицу;
- варианты ответов;
- количество баллов;
- объяснение правильного ответа.

В дальнейшем архитектура должна позволять добавлять аудио- и видеоматериалы.

---

# 12. Загрузка тестов

Система должна поддерживать два способа создания тестов.

### Вариант 1 — через веб-конструктор

Преподаватель вручную создаёт вопросы и ответы.

### Вариант 2 — импорт

Необходимо предусмотреть импорт тестов из структурированного шаблона.

Для первой версии рекомендуется обязательная поддержка:

**XLSX / Excel.**

Для этого администратор предоставляет стандартный шаблон:

| № | Вопрос | Ответ A | Ответ B | Ответ C | Ответ D | Правильный ответ | Балл |
| - | ------ | ------- | ------- | ------- | ------- | ---------------- | ---- |

После загрузки система должна:

1. проверить структуру файла;
2. проверить обязательные поля;
3. определить ошибки;
4. показать предварительный просмотр;
5. импортировать тест после подтверждения преподавателя.

Импорт непосредственно из произвольных DOCX/PDF-файлов не должен считаться обязательной функцией MVP, поскольку такие документы могут не иметь однозначной структуры. Его можно реализовать отдельным модулем позднее.

---

# 13. Назначение тестирования

Учитель выбирает:

**Тест → класс/группу → учащихся → параметры → назначить.**

Можно назначать:

- всей группе;
- нескольким группам;
- отдельному учащемуся;
- нескольким выбранным учащимся.

Параметры назначения:

- дата начала;
- дата окончания;
- продолжительность;
- количество попыток;
- минимальный проходной балл;
- разрешение просмотра результата;
- разрешение просмотра правильных ответов после завершения.

---

# 14. Процесс прохождения теста

После входа ученик открывает раздел:

**Мои тесты**

Тесты отображаются по статусам:

- Доступные;
- Запланированные;
- Выполненные;
- Просроченные.

После нажатия **«Начать тест»** система должна:

1. проверить право доступа;
2. проверить срок тестирования;
3. проверить количество оставшихся попыток;
4. создать попытку;
5. запустить таймер, если установлен лимит времени;
6. отображать вопросы.

---

# 15. Интерфейс прохождения теста

В интерфейсе необходимо отображать:

- название теста;
- номер текущего вопроса;
- общее количество вопросов;
- таймер;
- варианты ответа;
- кнопку «Назад»;
- кнопку «Далее»;
- индикатор отвеченных вопросов;
- кнопку «Завершить тест».

Перед окончательной отправкой система должна показать предупреждение:

**«Вы действительно хотите завершить тест? После подтверждения изменить ответы будет невозможно».**

---

# 16. Автоматическое сохранение ответов

Ответы учащегося должны периодически автоматически сохраняться.

Также ответ должен сохраняться после:

- выбора варианта;
- перехода на следующий вопрос;
- перехода на предыдущий вопрос.

При случайном обновлении страницы пользователь не должен терять уже сохранённые ответы.

---

# 17. Завершение тестирования

Тест может завершиться:

1. по инициативе учащегося;
2. автоматически после истечения времени;
3. автоматически после наступления крайнего срока в соответствии с правилами назначения.

После завершения попытка получает статус:

**Завершено.**

Ответы блокируются от изменения.

---

# 18. Проверка результатов

После завершения система автоматически сравнивает ответы учащегося с ключами теста.

Базовая формула:

**Результат (%) = Набранные баллы / Максимальные баллы × 100**

Система должна сохранять:

- количество правильных ответов;
- количество неправильных ответов;
- количество пропущенных вопросов;
- набранный балл;
- максимальный балл;
- процент;
- время прохождения;
- дату и время начала;
- дату и время завершения.

---

# 19. Страница результата учащегося

В зависимости от настроек преподавателя учащемуся может быть показано:

- итоговый балл;
- процент;
- количество правильных ответов;
- количество неправильных ответов;
- статус прохождения;
- правильные ответы;
- пояснения к вопросам.

Преподаватель должен иметь возможность отключить показ правильных ответов.

---

# 20. Аналитика преподавателя

Одним из ключевых компонентов системы является аналитическая панель.

Преподаватель должен видеть:

**Средний результат группы**

Например:

**74 %**

Дополнительно:

- количество учащихся;
- количество завершивших тест;
- количество не прошедших тест;
- максимальный результат;
- минимальный результат;
- средний балл;
- распределение результатов;
- среднее время выполнения.

---

# 21. Анализ вопросов

По каждому вопросу система должна рассчитывать как минимум:

- сколько учащихся ответили правильно;
- сколько ответили неправильно;
- сколько пропустили вопрос;
- процент правильных ответов;
- распределение выбранных вариантов.

Пример:

**Вопрос №7**

Правильно: 34 %
Неправильно: 61 %
Не отвечали: 5 %

Это позволит преподавателю выявлять вопросы или темы, вызвавшие наибольшие затруднения.

---

# 22. Аналитика по ученику

Учитель должен иметь возможность открыть карточку отдельного учащегося.

Необходимо отображать:

- ФИО;
- группу;
- список пройденных тестов;
- результаты;
- средний процент;
- количество попыток;
- динамику результатов;
- слабые темы при наличии достаточных данных.

---

# 23. Аналитика по группе

Для группы необходимо предоставлять:

- средний балл;
- средний процент;
- количество учащихся;
- рейтинг результатов, если такой режим разрешён;
- количество прошедших;
- количество не прошедших;
- сложные вопросы;
- распределение оценок/процентов.

---

# 24. Фильтры

Аналитические данные должны фильтроваться по:

- периоду;
- предмету;
- группе;
- преподавателю;
- тесту;
- учащемуся;
- статусу;
- результату.

---

# 25. Отчёты

Система должна формировать отчёты:

### Отчёт по тесту

Содержит результаты всех участников конкретного теста.

### Отчёт по ученику

Содержит историю результатов конкретного учащегося.

### Отчёт по группе

Содержит сводную информацию по группе.

### Сводный административный отчёт

Содержит общую статистику использования платформы.

---

# 26. Экспорт данных

Необходимо предусмотреть экспорт результатов как минимум в:

- XLSX;
- CSV.

В расширенной версии:

- PDF.

Экспортируемый отчёт должен содержать:

- название теста;
- предмет;
- группу;
- учащихся;
- баллы;
- проценты;
- дату прохождения;
- время прохождения.

---

# 27. Журнал аудита

Система должна вести централизованный **Audit Log**.

Каждое значимое действие должно регистрироваться.

Например:

- регистрация пользователя;
- вход;
- неудачная попытка входа;
- выход;
- создание теста;
- изменение теста;
- удаление/архивирование теста;
- публикация теста;
- назначение теста;
- начало тестирования;

- экспорт данных;
- изменение настроек системы.

# 28. Структура записи аудита

- роль;
- тип действия;
- объект действия;
- идентификатор объекта;
- дату;
- точное время;
- результат операции;
- IP-адрес, если его хранение допустимо принятой политикой;
- технические сведения, необходимые для расследования инцидента.

Критически важные записи журнала аудита не должны редактироваться через обычный пользовательский интерфейс.

Физическое удаление пользователя с потерей связанных результатов должно быть ограничено.

Предпочтительно использовать деактивацию/архивирование.

Особое внимание необходимо уделить одновременному началу тестирования большим количеством учащихся.

Конкретные нормативы количества одновременных пользователей должны быть определены после определения планируемого масштаба внедрения.

# 49. Критерии приёмки

Система считается функционально готовой к первичной приёмке, если выполняются следующие сценарии.

### Сценарий №1. Регистрация

Пользователь может зарегистрироваться по номеру телефона или через Google и войти в систему.

### Сценарий №2. Создание теста

Преподаватель может создать тест, добавить вопросы, определить правильные ответы и сохранить его.

### Сценарий №3. Назначение

Преподаватель может назначить созданный тест группе учащихся.

### Сценарий №4. Прохождение

Учащийся видит назначенный тест, проходит его и отправляет ответы.

### Сценарий №5. Проверка

После завершения система автоматически рассчитывает результат.

### Сценарий №6. Результат

Учащийся получает разрешённую преподавателем информацию о результате.

### Сценарий №7. Отчёт преподавателя

Преподаватель видит список учащихся и результаты тестирования.

### Сценарий №8. Аналитика

Система показывает статистику правильных и неправильных ответов и позволяет определить наиболее сложные вопросы.

### Сценарий №9. Администрирование

Администратор может управлять пользователями, ролями и группами.

### Сценарий №10. Аудит

Все критические действия появляются в журнале аудита, а пользователь с ролью «Аудитор» может просматривать эти данные без возможности их изменения.

---

# 50. Ожидаемый результат проекта

Результатом разработки должна стать единая веб-платформа, позволяющая организовать полный цифровой цикл проверки знаний:

**создание теста → назначение → электронное прохождение → автоматическая проверка → сохранение результатов → аналитика → отчётность → аудит.**

Платформа должна снизить объём ручной проверки, исключить необходимость постоянной работы с бумажными тестами и предоставить преподавателю структурированные данные для анализа успеваемости учащихся.

При этом архитектура проекта должна позволять в дальнейшем развить систему от обычного электронного тестирования до полноценной интеллектуальной образовательной платформы.
